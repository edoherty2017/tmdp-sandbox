PROVENANCE / LIMITATIONS:
  - Authored, not sampled from deployment traffic: executed/blocked rates characterize the gate on this constructed set, not a deployment risk rate.
  - No verbatim SafeToolBench items are used — only the abstract/figure text was reachable at run time; item text is our own.
  - 40 scenarios make the calibration bins sparse; ECE/MCE are indicative.
  - The mock effect tools have no real side effects; PROCEED executes a canned confirmation, so the demo measures gate decisions, not tool outcomes.
  - Labels are author judgements about a single pending call in isolation; a real deployment would weigh fuller session context.
  - Agent-demo backend behavior: the planner LLM is the local Claude Code CLI, which by design declines to volunteer structured tool-call plans for this harness framing — for risky requests it refuses upstream (a valid first line of defense, e.g. EXFIL-1 ends in a one-step refusal). So the demo SEEDS each scenario's canonical pending action to exercise the gate-in-the-loop on a concrete proposal; the gate decision, rule/LLM/combined scores, and the model's follow-up reaction are all real. The GATE EVAL (section A) exercises the full risk-judge -> T-MDP pipeline on all scenarios without seeding.
